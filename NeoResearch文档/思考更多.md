## 1. Research object model：把科研过程对象化

这是我认为最值得补充的一点。NeoResearch 不应只管理文件和日志，而应把整个研究流程抽象为一组标准化的 **Research Objects**。例如：

| Research Object         | 含义                                          |
| ----------------------- | --------------------------------------------- |
| **Task Object**         | 用户需求、任务边界、预测目标、评价指标、约束  |
| **Data Object**         | 数据 schema、数据版本、切分方式、数据质量诊断 |
| **Knowledge Object**    | 文献卡片、领域知识、方法经验、外部证据        |
| **Hypothesis Object**   | 研究假设、依据、预期收益、验证方式            |
| **Model Recipe Object** | 模型结构、输入输出、训练策略、约束条件        |
| **Experiment Object**   | 实验配置、运行日志、指标、checkpoint          |
| **Reflection Object**   | 失败归因、改进建议、下一轮计划                |
| **Release Object**      | 代码、参数、报告、模型卡、API 接口            |

这样 NeoResearch 的核心就不是“多个 Agent 顺序执行”，而是 **多个 Agent 共同创建、修改、验证和发布 Research Objects**。这个设计会让系统更清晰，也更容易扩展、复现和评估。

> **NeoResearch 应将科研过程对象化管理，而不是只依赖对话历史或零散脚本推进任务。**

## 2. Evidence lineage：建立从证据到结论的链路

NeoResearch 的研究结论必须能追溯。比如最终报告中说“多尺度周期模块有效”，系统需要知道这个结论来自哪里：

> 数据诊断发现强周期性 → HypoPlanner 提出多尺度周期建模假设 → ModelDesigner 设计多尺度模块 → TrainEval 完成对比实验 → Reflector 判断该假设被部分验证 → ResultPublisher 写入最终报告。

这就是 **evidence lineage**。它可以让 NeoResearch 的输出从“看起来合理”变成“有证据链支撑”。

建议每个关键决策都记录：

```
{
  "decision": "adopt multi-scale seasonal modeling",
  "evidence": [
    "DataDiagnoser found strong daily and weekly seasonality",
    "Literature Agent retrieved related decomposition-based TSF methods",
    "Experiment run_004 improved MAE over baseline by 8.3%"
  ],
  "made_by": "HypoPlanner + ModelDesigner",
  "verified_by": "TrainEval + Reflector"
}
```

这对科研系统很重要，因为科研不只是产出结论，更要说明结论如何产生。

## 3. Autonomy level：定义不同自主级别

NeoResearch 不一定所有任务都要完全自主执行。建议设计不同的自主等级。

## 4. Failure taxonomy：建立失败类型体系

自主研究系统一定会失败，而且失败会非常多样。NeoResearch 需要提前设计失败分类，而不是等系统崩了再让 LLM 临时解释。

可以把失败分成几类：

| 失败类型                | 示例                                             |
| ----------------------- | ------------------------------------------------ |
| **Data Failure**        | 数据缺失严重、时间戳错误、数据泄漏、字段语义不清 |
| **Code Failure**        | 代码无法运行、依赖冲突、维度错误、训练脚本错误   |
| **Model Failure**       | 欠拟合、过拟合、训练不稳定、参数量超预算         |
| **Evaluation Failure**  | 指标计算错误、验证集污染、测试集反复使用         |
| **Reasoning Failure**   | 假设不可验证、反思无证据、文献知识误用           |
| **Resource Failure**    | GPU 不足、训练超时、存储不足                     |
| **Interaction Failure** | 用户需求不清、关键约束缺失、确认信息冲突         |

有了失败体系，Reflector Agent 才能更稳定地做失败归因与修复。否则反思容易变成泛泛而谈。

## 5. Post-release lifecycle：模型发布之后怎么办

如果 NeoResearch 要作为 **Model Factory**，那么模型交付不是终点。还需要考虑模型发布后的生命周期：

> 模型部署 → 在线调用 → 运行监控 → 漂移检测 → 性能衰减告警 → 自动再训练 → 新版本发布。

这对 Time Series Forecasting 特别重要，因为时序数据往往会随时间发生漂移。一个模型今天表现好，不代表三个月后仍然表现好。

因此 ResultPublisher Agent 后面甚至可以再扩展一个：

> **ModelMonitor Agent**

负责监控模型上线后的数据分布变化、预测误差变化和再训练触发条件。这样 NeoResearch 就从“一次性模型生产”走向“持续模型演化”。

## 6. Domain onboarding：领域知识如何进入系统

NeoResearch 服务领域数据挖掘工程师时，必须解决一个问题：**领域知识怎么进入 Agent Runtime？**

例如电力负荷预测、云服务流量预测、工业传感器预测、医疗时序预测，它们的数据机制和业务约束完全不同。系统不能只依赖字段名自动猜测。

建议设计一个 **Domain Card**：

```
domain: electric_load_forecasting
important_context:
  - weather
  - holiday
  - working_day
  - temperature
common_patterns:
  - daily seasonality
  - weekly seasonality
  - holiday effect
common_risks:
  - distribution shift
  - extreme weather events
  - missing external covariates
preferred_metrics:
  - mae
  - rmse
deployment_constraints:
  - low latency
  - stable daily update
```

这样 IntentScope、DataDiagnoser、HypoPlanner 和 ModelDesigner 都可以读取领域卡片，形成更有领域感的建模策略。

## 7. Experience memory：让系统从历史实验中学习

NeoResearch 不应每次从零开始。它应该沉淀历史任务中的经验，例如：

> 某类电力负荷数据适合哪些模型；某类高噪声小样本数据不适合复杂 Transformer；某类强周期数据中分解结构常常有效；某些实验失败通常由窗口长度不合理导致。

这可以形成：

```
experience_memory/
├── successful_recipes/
├── failed_recipes/
├── dataset_lessons/
├── domain_lessons/
├── model_performance_records/
└── reflection_cases/
```

长期看，NeoResearch 的能力提升不只来自更强 LLM，也来自这些历史经验的积累。这个点很适合和你的 Agentic AI / Memory 主线结合。



## 9. Evaluation of NeoResearch itself：系统自身如何被评估

NeoResearch 做出来后，需要评估的不只是模型性能，还要评估这个 Agent 系统本身。可以考虑：

| 维度         | 指标                                        |
| ------------ | ------------------------------------------- |
| **自主性**   | 人工干预次数、自动完成率                    |
| **可靠性**   | 成功运行率、失败恢复率                      |
| **科研质量** | 假设合理性、实验设计质量、反思是否基于证据  |
| **工程质量** | 代码可运行率、复现成功率                    |
| **效率**     | 总运行时间、实验次数、GPU 成本、token 成本  |
| **交付质量** | 报告完整性、artifact 完整性、模型接口可用性 |
| **用户价值** | 是否减少人工时间、是否提升模型迭代效率      |

这个评估体系可以成为 NeoResearch 论文中的一个重要贡献点。



## 10. Product narrative：避免被理解成 AutoML

最后还要注意产品叙事。NeoResearch 很容易被别人误解成“又一个 AutoML / AutoTS”。所以你需要反复强调它的差异：

> AutoML 关注模型搜索，NeoResearch 关注自主研究闭环。
>  AutoML 优化指标，NeoResearch 形成假设、设计实验、验证结论并发布成果。
>  AutoML 输出模型，NeoResearch 输出可复现研究交付包。
>  AutoML 服务单次任务，NeoResearch 可以作为 Agentic AI 生态中的 Model Factory。
