# 产品价值

产品定位、任务体系、数据体系、模型工厂、评估基准和交付机制，决定 NeoResearch 是否真正有价值。

## 1. 产品定位与用户场景

首先要明确 NeoResearch 面向谁。一类用户是 **领域数据挖掘工程师**，另一类用户是**上层 Agent 系统**。

对于领域数据挖掘工程师，NeoResearch 的价值是帮助他们从“手动分析数据、调模型、整理实验”转向“提出目标、监督关键节点、获得完整交付”。因此产品要重视自然语言任务创建、交互式需求澄清、实验进度可视化、结果解释和报告导出。

对于 Agent 系统，NeoResearch 的价值是作为 **Model Factory**。它需要根据任务和数据自动生产专用小模型，并提供标准化接口，让其他 Agent 可以调用这些模型。因此这里不仅要输出 checkpoint，还要输出 model card、API schema、inference script 和调用说明。

## 2. 任务体系与问题边界

NeoResearch 不能一开始就泛化到所有 Data Science 任务。建议先把 **Time Series Forecasting** 作为主战场，定义清楚支持哪些任务类型。

例如：

| 任务类型         | 示例                                   |
| ---------------- | -------------------------------------- |
| 单变量预测       | 未来电力负荷、流量、温度预测           |
| 多变量预测       | 多传感器、多站点、多指标联合预测       |
| 带协变量预测     | 加入天气、节假日、事件、价格等外部变量 |
| 长期预测         | 长 horizon 的趋势预测                  |
| 异常敏感预测     | 对突变、异常点、非平稳变化敏感的预测   |
| 轻量化小模型设计 | 面向部署约束自动设计小模型             |

这样 NeoResearch 的能力边界会更清楚，也便于后续做 Benchmark 和论文实验。



## 3. 数据体系设计

NeoResearch 是面向 Data Science 的系统，所以数据层非常关键。你需要设计一个标准化的 **Data Layer**，让不同领域的时序数据可以被系统统一读取、诊断、切分和评估。

数据层至少要包括：

```
数据上传与连接
数据 schema 识别
时间戳解析
采样频率识别
缺失值检测
异常值检测
train/val/test 切分
数据泄漏检查
数据版本管理
Data Card 生成
```

尤其是 Time Series Forecasting，要非常重视数据切分和数据泄漏。NeoResearch 如果反复使用测试集做反思，很容易产生评估污染。因此建议设计一个 **Evaluation Firewall**，让训练集、验证集、测试集和 hidden test set 的使用边界非常明确。

## 4. Model Recipe DSL 与模型设计空间

NeoResearch 的目标不是只调用已有模型，而是帮助用户迭代与设计时序小模型。因此你需要定义一个 **Model Recipe DSL**，让 ModelDesigner Agent 生成的模型方案不是随意自然语言，而是结构化、可执行、可编译的模型配方。

例如：

```
model_name: MultiScaleTinyForecaster
input:
  history_window: 96
  prediction_horizon: 24
  covariates: true
architecture:
  backbone: temporal_conv
  decomposition: true
  multiscale_blocks: 3
  attention: lightweight
training:
  loss: mse
  optimizer: adamw
  learning_rate: 0.001
  batch_size: 64
constraints:
  max_params: 5M
  latency_sensitive: true
```

这样 NeoResearch 就不是“让大模型随便写一个模型”，而是在一个受控的模型设计空间中自动组合、搜索和验证。这个设计非常重要，因为它决定 NeoResearch 是否能成为真正的 **Model Factory**。



## 5. 文献知识与研究知识库

你已经提出 Literature Search Agent，这个非常重要。但还需要进一步设计知识如何沉淀。NeoResearch 不能每次都从零查论文，而应该逐步形成自己的研究知识库。

可以设计几类知识：

| 知识类型           | 内容                                   |
| ------------------ | -------------------------------------- |
| Paper Cards        | 论文方法、适用场景、局限性、可迁移思想 |
| Dataset Cards      | 数据集特征、领域背景、常见挑战         |
| Model Cards        | 模型结构、输入输出、适用条件、性能记录 |
| Experiment Lessons | 某类实验失败或成功的经验               |
| Failure Cases      | 过拟合、欠拟合、漂移、数据泄漏等案例   |
| Skill Cards        | 可复用技能的描述、输入输出和适用范围   |

这里要注意一个原则：

> **文献知识不是答案，而是假设来源。**

Literature Agent 检索到的论文观点不能直接进入模型设计，而应先被 HypoPlanner 转化为可验证假设，再由实验验证。



## 6. 评估体系与 Benchmark

NeoResearch 本身也需要被评估。否则它只是一个系统 Demo，很难形成学术贡献。建议你设计两层评估。

第一层是 **模型结果评估**，即 NeoResearch 自动设计的小模型在 TSF 任务上的预测性能、效率和鲁棒性。

第二层是 **Agent 过程评估**，即 NeoResearch 作为自主研究智能体是否真的有效。

可以考虑这些指标：

| 评估维度     | 指标示例                                       |
| ------------ | ---------------------------------------------- |
| 任务完成能力 | 完成率、失败率、需要人工干预次数               |
| 代码质量     | 可运行率、单元测试通过率、复现成功率           |
| 模型性能     | MSE、MAE、相对 baseline 提升                   |
| 成本效率     | 实验次数、运行时间、token 成本、GPU 成本       |
| 研究质量     | 假设合理性、实验计划可执行性、反思是否基于证据 |
| 交付质量     | 报告完整性、代码完整性、artifact 可复现性      |

这一部分可以成为 NeoResearch 论文或系统报告的核心实验设计。

## 7. 用户交互与产品体验

NeoResearch 既然有苏格拉底式和认知伴随式两种模式，就需要在产品界面上体现出来。

建议至少设计几个核心界面：

```
任务创建页：选择交互模式、上传数据、描述目标
研究工作区：展示当前阶段、To-do List、Agent 状态
数据诊断页：展示趋势、周期、异常、风险和建模启发
假设规划页：展示研究假设和实验计划，支持用户确认
实验看板：展示实验运行状态、指标、日志、失败原因
结果发布页：展示报告、代码、模型权重、复现说明
```

产品体验上要强调：用户不是在和一个聊天机器人对话，而是在使用一个 **研究工作台**。

## 8. 结果交付与 Model Factory 接口

ResultPublisher Agent 输出的不应只是 `final_report.md`。如果 NeoResearch 要成为 Model Factory，最后的交付包应该标准化。

建议包括：

```
final_report.md / pdf
README.md
model_card.md
model.py
checkpoint.pt
config.yaml
train.py
evaluate.py
inference.py
metrics.csv
prediction_outputs.csv
requirements.txt
artifact_manifest.json
api_schema.yaml
```

其中 `model_card.md` 和 `api_schema.yaml` 很关键。它们决定这个小模型能否被其他 Agent 或外部系统调用。

可以把最终交付定义为：

> **Research Release Package = Code + Checkpoint + Config + Metrics + Logs + Report + Model Interface**

这会让 NeoResearch 从“自动实验系统”升级为“模型生产与交付系统”。

## 9. 安全、权限与资源控制

NeoResearch 会读写文件、运行代码、训练模型、访问文献、生成报告，因此必须考虑安全和资源边界。

需要注意：

```
哪些目录可以读写
哪些操作需要用户确认
是否允许联网搜索
是否允许覆盖已有文件
是否允许删除实验结果
训练预算上限是多少
最大实验轮数是多少
最大模型参数量是多少
是否允许对外发布结果
```

尤其是如果未来 NeoResearch 作为服务部署给团队使用，就需要任务隔离、文件权限、数据隐私和日志审计。
