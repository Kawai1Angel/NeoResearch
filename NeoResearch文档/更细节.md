## 1. Model recipe compiler：从模型想法到可运行代码的编译层

这是一个很关键但容易被忽视的模块。NeoResearch 不应该让 ModelDesigner Agent 直接自由生成完整代码。更稳妥的方式是让它先生成结构化的 **Model Recipe**，然后由一个 **Compiler / Builder** 将 recipe 转换成可运行代码。

也就是说：

> **ModelDesigner 负责提出模型配方，Model Compiler 负责把模型配方编译成可靠代码。**

例如 ModelDesigner 输出：

```
model:
  backbone: temporal_conv
  decomposition: true
  multiscale: true
  attention: lightweight
training:
  loss: mse
  optimizer: adamw
```

然后 Compiler 根据预定义组件库生成 `model.py`、`config.yaml`、`train.py`。这样可以减少 LLM 直接写代码带来的不稳定性，也能让模型设计空间更加可控。

这个模块可以叫：

> **ModelCompiler Agent / RecipeCompiler**

它会让 NeoResearch 更像真正的 **Model Factory**，而不是“让 LLM 随机写模型代码”。

## 2. Component library：可组合模型组件库

如果 NeoResearch 要持续设计时序小模型，就需要一个可组合的模型组件库。否则每次都从零生成代码，系统不稳定，也不利于复现。

组件库可以包括：

```
Decomposition Block
Temporal Convolution Block
Patch Embedding Block
Frequency Block
Lightweight Attention Block
GRU/LSTM Block
Residual Block
Normalization Block
Covariate Fusion Block
Uncertainty Head
Forecasting Head
```

ModelDesigner Agent 不一定直接写完整模型，而是从这些组件中组合新结构。这样 NeoResearch 的模型设计会更像“架构搜索 + 模块组合”，而不是自由生成。

可以形成一个核心设计：

> **NeoResearch designs models by composing verified forecasting components, rather than generating arbitrary neural architectures from scratch.**

中文可以写成：

> **NeoResearch 通过组合经过验证的时序建模组件来设计模型，而不是从零自由生成不可控的神经网络结构。**



## 4. Versioning：任务、数据、模型、实验和报告都要版本化

NeoResearch 如果要成为研究平台，版本管理非常重要。每一次数据诊断、模型设计、实验运行和报告发布都应该有版本。

例如：

```
task_spec_v1.yaml
data_diagnosis_v2.md
model_recipe_v3.yaml
experiment_run_012
final_report_v1.md
```

这样用户可以追溯不同版本之间的变化。比如某次实验提升是因为换了模型结构，还是因为改了数据切分方式，还是因为修正了评价指标。

可以设计统一版本关系：

> **Task Version → Data Version → Recipe Version → Experiment Version → Release Version**

这会显著增强 NeoResearch 的科研可审计性。



## 5. Trust calibration：结果可信度与不确定性表达

NeoResearch 不能只输出“我找到了最优模型”。它还需要告诉用户：这个结果有多可信，哪些结论只是初步发现，哪些结论已经被实验验证，哪些地方仍然不确定。

例如最终报告中可以区分：

```
Verified findings：已有实验支持的发现
Tentative hypotheses：仍需进一步验证的假设
Known limitations：当前模型或实验的局限
Risk warnings：可能存在的数据、评估或部署风险
```

这对科研场景很重要。因为自主研究智能体最容易出现的问题是“表达得很自信，但证据并不充分”。

所以 NeoResearch 的 ResultPublisher Agent 应该具备 **可信度标注** 能力。



## 6. User correction loop：用户纠错如何进入系统

在认知伴随式模式中，用户不仅是确认者，也应该能纠正系统的误判。比如用户可以说：

> “这个字段不是外部协变量，而是未来不可获得变量。”
>  “这个异常点不是噪声，而是业务事件。”
>  “这个数据不能随机切分，只能按时间顺序切分。”
>  “这个模型太大，不符合部署要求。”

这些用户反馈不应只停留在聊天记录里，而应该写入结构化文件，例如：

```
user_corrections:
  - field: "temperature_forecast"
    correction: "available only at prediction time"
  - field: "holiday_flag"
    correction: "should be treated as known future covariate"
```

这样后续 Agent 才能真正吸收用户知识。

这可以叫：

> **Human Feedback Memory / User Correction Memory**

## 7. Deployment adapter：从研究模型到可部署模型

如果 NeoResearch 设计的小模型最终要服务真实场景，就需要考虑部署适配。模型不仅要训练好，还要能被调用、监控和更新。

ResultPublisher 之后可以输出：

```
inference.py
api_schema.yaml
model_card.md
requirements.txt
dockerfile
example_request.json
example_response.json
```

如果进一步产品化，还可以支持：

```
REST API
Batch inference
Streaming inference
ONNX export
TorchScript export
Edge deployment
```

这会让 NeoResearch 从“研究实验平台”走向“模型生产平台”。



## 8. Multi-run learning：跨任务学习与经验迁移

NeoResearch 的长期价值不只是完成单次任务，而是随着任务数量增加，系统越来越会做研究。

例如它可以逐步学到：

```
电力负荷数据常常需要日周期和周周期建模
云服务流量数据常常存在突发事件和分布漂移
小样本高噪声数据不适合复杂 Transformer
强周期数据中分解模块通常值得优先尝试
长期预测任务中直接多步预测可能比递归预测更稳定
```

这些经验可以作为后续任务的先验知识。长期看，这部分比单次 Agent 推理更有价值。

可以将其定义为：

> **Experience-conditioned autonomous research**

也就是：NeoResearch 不仅基于当前数据和文献做研究，还基于历史研究经验做研究。

## 9. Benchmark-driven development：系统开发要被 Benchmark 驱动

NeoResearch 自己的开发也需要 Benchmark。否则每次改 Agent、改 Skill、改 workflow，都不知道系统是否真的变好。

可以构建一组固定任务：

```
简单单变量预测任务
多变量预测任务
强周期任务
非平稳漂移任务
小样本任务
带协变量任务
高噪声任务
长预测窗口任务
```

每次更新 NeoResearch，都运行这些任务，比较：

```
任务完成率
代码运行率
实验复现率
模型性能
运行成本
人工干预次数
报告质量
```

这样 NeoResearch 会形成自己的持续评测体系。这个也可以和你正在构建的 FutureCast 形成联动。
