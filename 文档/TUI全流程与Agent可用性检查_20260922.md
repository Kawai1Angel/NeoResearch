# TUI 全流程与 Agent 可用性检查

检查日期：2026-09-22。对象：当前工作区的 `opencode/packages/opencode` 与 `neo_cast`。

## 结论

**TUI 可以启动，Python 训练后端可以运行；但目前不能判定“用户从 TUI 进入后，所有 Agent 都能正常完成全流程”。**

本次实际启动了首页并进入 Cockpit，完成类型检查、Research/TUI/API 定向测试和 Neo-Cast 全部 npm 测试。发现三个经独立复现确认的功能缺口，以及长任务超时与后端取消没有衔接的问题。未修改业务代码。

当前启动环境的首页提示 Configure API Key，默认 Anthropic 环境变量未配置。本次没有完成真实 provider 的需求对话到最终报告的全链路实验，不能用模拟测试代替这一验收。

## 确认的问题

### P1：PublishAgent 的 Session 身份未注册，默认配置下无法执行 LLM 报告生成

- `src/research/service.ts:8671` 调用 `requestViaSession`，指定 `agent: "research-publish"`。
- `src/agent/agent.ts:239` 起的内置 Agent 列表包含 intent、data-analysis、literature、hypo-planner、reflection、model-designer，但没有 research-publish。
- `src/session/prompt.ts:887` 对不存在的 Agent 抛出 `Agent not found`。
- `src/research/service.ts:3492` 附近的 `requestViaSession` 捕获异常并返回 undefined；Publish 随后使用 `renderDeterministicFinalReport`。

复现：在隔离配置下读取实际 Agent registry，`research-publish` 不存在。即使配置了有效模型，默认内置配置仍缺少该身份。用户自行配置同名 Agent 可以改变结果，但这不属于开箱可用。

影响：模型包及模板报告仍可能成功产出，不能据此声称 Publish 的 LLM Agent 已正常工作。

建议：注册专用 Publish Agent，并增加调用真实 Session 路径的集成测试；报告中明确展示是否使用降级模板。

### P1：TUI 配置的 provider 密钥不能被文献提取模块一致使用

- `src/research/literature/extraction-model.ts:110` 直接调用 `resolveNeoCastLLMConfig` + `apiKeyFor`，只检查环境变量。
- 其他研究模块使用 `src/research/llm-proposal.ts:1046` 的 `resolveEffectiveLLMConfig`，支持从 auth.json 回退读取密钥。
- `src/research/literature/literature-agent.ts:190` 在模型不可用时返回 partial、空 cards，并记录 `llm_not_configured`。

复现：在隔离目录写入假的 OpenAI auth.json 密钥，不发起网络请求。共享 resolver 返回可用配置，而 `ConfiguredLLMExtractionModel.create()` 返回 undefined。

影响：只通过 TUI 配置密钥的用户，可能看到其他 Agent 工作正常，Literature 检索流程也完成，但论文知识提取没有发生。已有知识库卡片是否可复用是另一回事。

建议：文献提取统一使用共享凭据解析器，并把“无提取模型”“无论文证据”作为不同状态显示。

### P1：Companion 拒绝检查点后，重新推进会生成相同的待审批检查点

- `src/research/service.ts:4133` 的 `ensureHumanCheckpoint` 只查 approved 和 pending，忽略 rejected。
- `replyApproval` 仅对 intent_confirmed 的拒绝提供专门回退处理。
- experiment_budget_extended 提示“reject 接受当前结果”，但下一次运行无法取回 rejected 状态，会再次创建 pending；final_model_selection/report_release 的拒绝也未形成相应终止分支。

复现：沿现有 Companion service 测试运行至 search_space_confirmed，拒绝，再调用 pipeline；产生新的同名 pending 检查点，ID 与被拒绝项不同。

影响：Companion 的否决、接受当前预算结果、终止发布等交互语义不完整，用户可能反复回到同一个确认环节。

建议：根据检查点类型处理 rejected；有意重新请求确认时，应要求输入或状态已发生变化。

### P1：长训练流程仍绑定同步 HTTP 请求，超时/取消未传递到后端任务

此项为调用链静态确认，未等待十分钟进行超时复现。

- `src/cli/cmd/tui/routes/research-cockpit.tsx:3048` 的 pipeline 请求允许最多 50 轮，但请求超时固定为 600,000 ms。
- 不走 pipeline 的 autonomous loop 使用 `researchRequest` 默认 90,000 ms。
- `src/server/routes/instance/research.ts:610` 同步等待整个 `runFullPipeline`。
- `src/server/routes/instance/trace.ts:46` 的 `runRequest` 没有将请求中断信号传给 Effect；runner 的 AbortController 是其自身超时/watchdog 使用，未接入 TUI 请求的 signal。

影响：训练或文献处理较久时，前端可能显示超时、退出 busy，后端仍继续；用户再次提交可能与尚未完成的任务重叠。现有 literature 锁不能替代完整 pipeline 的任务互斥。

建议：将流水线作为后台任务启动，通过事件订阅获取状态；增加任务级互斥、取消和断线恢复。仅增大 HTTP 超时不能解决状态一致性。

## 37 项失败如何解读

| 测试文件 | 失败数 |
| --- | ---: |
| CLI research-command | 2 |
| CLI research-data | 1 |
| e2e-autonomous-loop | 1 |
| tsf-domain | 8 |
| server research-routes | 19 |
| TUI research-cockpit-render | 6 |

不能将 37 个失败直接解释为 37 个产品 bug：

- 部分测试仍预期 3 个 baseline，当前实现返回 1 个，属于预期与现实现的漂移。
- 模拟 E2E/API runner 没有产生当前门禁要求的 executed manifest/verification，报 `execution_contract_violation`。这说明旧测试没有适配门禁，不证明真实 Python runner 一定失败，也不应通过移除门禁解决。
- TUI 失败涉及 onboarding、slot-fill、任务切换、候选选择和旧布局断言；其中包含界面已变化但断言未同步的情况，仍需逐项核实。
- 独立缺陷复现的 3 个失败是额外运行的测试，不包含在上述 37 项中。

## 修复与验收顺序

1. 修复 Publish 注册、Literature 凭据解析、Companion rejected 分支。
2. 完成后台流水线、任务互斥、取消和恢复处理。
3. 更新集成 fixture，使其真实满足执行契约，修复 TUI 交互回归。
4. 使用已配置 provider 和小型 CSV，从 TUI 分别完成 Socratic 与 Companion：需求确认 → 数据分析 → 文献证据 → 假设 → 至少一次真实训练 → 验证与反思 → ref-test → 模型包与报告，并验收 reject、超时、重入和恢复。
