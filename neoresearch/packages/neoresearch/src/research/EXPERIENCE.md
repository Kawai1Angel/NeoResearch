# Research experience

Every saved experience has **all three parts**. They are not mutually exclusive entry types:

| Part | Content | Purpose |
| --- | --- | --- |
| `organization.experimentFacts` | Dataset identity/profile, actual model, proposed training recipe, named control, metrics, failures and artifact references | Traceable experimental evidence |
| `organization.conditionalExperience` | Under stated data/recipe conditions, an operation has a stated expected effect; observed contrasts, boundaries and a falsifiable validation plan | Generate hypotheses for compatible tasks |
| `organization.validatedRegularity` | Supporting dataset contents, counterexample datasets, qualifications, unassessed observations, missing validation and scope review | Guide search order and budget according to the strength and limits of accumulated evidence |

`level` is retained only as a backward-compatible maturity label. It does not select which parts exist and is not a substitute for the computed validation state.

## Organization and evolution

Source `research_experience.v1` memories remain append-only. All entries have a persisted three-part organization in shared SQLite: `research_experience_organization` maps each experience ID to its `threadID`, and `research_experience_thread` stores the accumulated three-part record once per thread. The organization can be rebuilt from source entries and their persisted curation reviews and is included by the native tool, direct transport, CLI and task export paths. Compact reads show all three parts; full actual models/training recipes/profiles and all thread evidence are available with `experienceID` and `includeFacts=true`.

A new write supplies `evolution.claim` with `statement`, `dataConditions`, `operation`, `interventionPaths`, `expectedOutcome` (`metric`, `direction`, and an absolute `equivalenceMargin` for `equivalent`), `boundaries` and `validationPlan`. Outcome directions are `lower`, `higher`, `equivalent`, `execution_success` or `execution_failure`. These are explicit hypotheses, not certified causal explanations. Actual data profiles and results come from captured facts, never from agent-supplied factual metrics.

To test an existing explicit claim, first retrieve the relevant shared proposition and read its exact ID, then submit `evolution={parentExperienceID,relation}` and only the new local run/control evidence. Relation is `supports`, `refutes`, `qualifies` or `observes` **with respect to the stable parent's claim**. It is separate from local polarity and from evidence references supporting the factual observation: an experiment with a worse metric may correctly support a factual negative observation while refuting the parent's predicted improvement. Structured root claims in the same domain join automatically only when their scientific fields match after normalizing whitespace, condition/boundary order and recipe path aliases. A changed future validation plan does not create a different proposition. Similar prose never suffices to merge hypotheses. Parent and child claims cannot silently change meaning. A revised scope or mechanism requires a new root claim with `derivedFrom` provenance.

The write receipt distinguishes `created` (a new logical experience) from `appended` (new evidence for the existing experience), and returns the stable canonical `experience.id`, `sourceEntryID` and current `revision`. Internally, `ExperienceLibrary.save().created` continues to indicate a new immutable source entry; `experienceCreated` and `appended` describe the logical experience. Default browsing and search use one entry per explicit experience thread. Exact `experienceID`, `threadID` and archive browsing retain access to individual source entries.

Each update recomputes the three parts together: immutable facts accumulate, `conditionalExperience.currentConclusion` summarizes support/counterexample/qualified/unassessed run IDs, and `validatedRegularity` updates dataset evidence and retains every recorded boundary. Canonical IDs survive later imports of older observations. Versions advance when the organized content changes, including curation, and an unchanged rebuild or exact write retry does not create a version. `research_experience_thread_version` persists conclusion/scope summaries and immutable source/run references without copying full model/training snapshots into every version. Exact reads with `includeHistory=true` expose those historical audit summaries; historical withdrawn interpretations are not current guidance. Native and bounded direct-mode reflection can retrieve an existing shared experience before deciding whether to append.

The thread accumulates every source entry, support, counterexample and boundary. Numerical claims require a matched verified full-run contrast that isolates the claim's declared recipe paths and metric. An observed opposite numerical outcome is preserved as counterevidence even if an agent labels it support. Mixed changes, missing controls, smoke failures or irrelevant metric contrasts remain unassessed for the performance claim. Source errors can test execution claims; they cannot refute a prediction-quality hypothesis. Diagnoses remain tentative. Identical citations do not become independent replications; copies of the same dataset content count once. Conflicting source snapshots are preserved and block validation.

Validation states are `not_validated`, `corroborated_pending_review`, `validated_in_scope`, and `contested`. At least two distinct supported dataset content hashes establish cross-dataset coverage; they do not automatically validate a mechanism. Optional `evolution.scopeReview` supplies every assessed run ID, conditions and implementation assessments, rationale, applicability boundaries and limitations. Only a review covering all current outcomes, with at least two supported dataset contents and no unresolved counterexamples, qualifications, unassessed outcomes or conflicting snapshots, can yield `validated_in_scope`. This is an evidence-gated model-authored scope review, not a guarantee of universal validity or statistical significance. New contrary evidence immediately yields `contested`; new unreviewed evidence requires renewed scope review. Reviews cannot erase prior counterexamples.

Historical entries are backfilled without rewriting raw facts or promoting their prose. They have all three parts, with `legacy_needs_formulation` and explicit missing validation where no structured claim was captured. Verified historical contrasts are organized into `conditionalExperience.observedRelationships`: captured data features and evaluation/configuration scope -> actual field changes -> observed metric contrast. Their proposed general explanations remain explicitly unverified. Old `derivedFrom` links remain visible as related provenance; they do not prove that two differently worded claims are the same hypothesis. Formulate a new explicit root referencing the historical IDs before continuing it. Legacy-compatible writes remain readable and similarly expose their missing formulation.

## Full-library curation

`research_experience_curation` stores a source-SHA256-bound review of each inspected entry, with a disposition, reasons, notes, reviewer and corrected interpretation. It changes read projections and derived organization; the original source JSON, captured facts and evidence relations remain unchanged. A stale source digest or changed evidence relation aborts the entire review transaction. Rebuilding organization re-applies these reviews, including in processes that already opened the library.

Dispositions are `retained` (useful content retained within its supported scope), `rewritten` (unsupported prose replaced by a factual, conditional interpretation), `merged` (duplicate interpretation archived under an active canonical ID), and `quarantined` (excluded from research use). Normal native, direct, CLI, task-memory and export reads exclude merged and quarantined records, even with background retrieval enabled. An exact merged ID resolves to the canonical record. Merges require identical captured evidence; they add no support votes or independent replications. Archived records cannot be continuation parents. Local task-table copies cannot resurrect globally archived experiences.

Use `includeArchived=true` for archive inspection and `includeOriginal=true` with an exact `experienceID` for original prose under `originalForAuditOnly`. CLI equivalents are `--include-archived` and `--include-original`. Original prose is audit material and must not be reused as a current conclusion. The three-part organization and current interpretation remain available alongside the review metadata.

A full review checks every referenced run against authoritative task metrics and actual model snapshots, then checks controls, changed fields, duplicate execution flags, artifact identity, fold values and training curves where available. Fold variation is not seed uncertainty or an equivalence test; a finite validation result is not an execution failure merely because an old acceptance rule rejected it. Reused artifacts without a new independent result do not establish another observation. New writes require a current-task independent observation: an actual error, or execution-confirmed metrics (a confirmed smoke execution is also allowed).

Historical single-contrast entries may receive an explicitly labeled hypothesis formulated after the observed result, scoped to measured data profiles, the complete joint intervention and its metric. They still require prospective replication and cross-dataset scope review. Other reviewed entries use `reviewed_observations` and retain their conditional configuration/operation/result relationships without inventing a unified hypothesis. Neither status establishes a validated regularity.

Query search keeps one matching revision per explicit thread while exposing other revision IDs; exact IDs and `threadID` browsing retain the entire history. Existing evidence-set deduplication still applies to legacy interpretations. Native/direct readers accept `threadID`; CLI uses `--thread-id`.

## Formation and storage

All runs and artifacts remain the experiment record. Successful runs still update the champion and persist the evaluation decision, including seed and secondary-metric checks, in `resourceUsage.evaluationDecision`. Creating or completing a run does not automatically add a research experience.

ReflectionAgent decides whether a result merits saving and may call `write_experience` zero or more times. Positive, negative, mixed and inconclusive experiences are supported. Its final `distillableMemory` is a report summary, not an implicit write. The direct API fallback can explicitly request the same validated operation through an optional `experienceWrites` array; omitted or empty arrays save nothing. Write outcomes are included in the persisted reflection result.

Each saved entry goes directly to the shared SQLite `research_experience` table with a versioned `candidateSummary.experience` payload (`research_experience.v1`). It contains the model-authored interpretation and separately captured facts: task/run/candidate IDs, dataset identity, task profile, evaluation settings, proposed recipe/training configuration, actual execution manifest, verification and independence flags, metrics, evaluation decision, errors and artifact IDs. Actual execution and proposed configuration are distinct fields. Exact retries are deduplicated transactionally by source project/task and content key. `derivedFrom` records provenance and retains legacy inherited evidence. Explicit `evolution` continuations accumulate the parent history in the organization rather than copying or relabeling prior evidence as a new local observation.

The outer legacy `outcome` is only a compatibility projection of polarity. Consumers must use the experience level, claim and evidence, rather than interpreting it as a champion decision. Structured experiences do not put a recipe in `candidateSummary.candidateSpec`, so their interpretations do not become positive/negative recipe-training labels in the legacy ranker.

New runs capture dataset and evaluation context at creation in `resourceUsage.experienceContext`, and preserve it across status updates. Dataset files receive full SHA-256 identities (cached while file metadata is unchanged). Copies with identical contents count as one dataset. Missing/unreadable dataset contents and historical runs without a run-time snapshot have unverified dataset identity and cannot establish a multi-dataset validated principle. A later edit to a CSV or task configuration does not change a new run's captured context.

Library selection uses the absolute `NEO_RESEARCH_EXPERIENCE_DB` override, then the nearest project `.neo-research/experience.db` or `.neo-research/experience-export/experience.db`, then `~/.neo-research/experience.db`. Existing validated structured project memories are copied idempotently on reads and writes, preserving IDs, timestamps and complete evidence. New experiences do not require source task/run rows in the receiving project database. `neo-research research experiences --path` reports the selected library; `neo-research research experiences --domain tsf` queries it without creating a research task.

## Evidence validation

- New references must resolve to finished runs in the current project and domain, with at least one source run from the writing task. Foreign facts can only be inherited from a named validated parent experience in the same domain; complete snapshots and counterevidence are retained.
- The writer accepts source references, not fabricated factual metrics or model snapshots.
- Conditional performance experiences require independent, verified full runs, finite primary metrics and a completed same-task comparison under the same dataset and evaluation settings.
- A validated principle needs support from at least two distinct dataset content hashes. Performance principles also require paired comparisons; execution principles require verified full successes or independently observed failures with error evidence. The count is a minimum evidence gate, not a claim of universal validity or statistical significance.
- Ref-test and blind-test outcomes cannot enter search experience.
- Refinements preserve inherited evidence relations; contradictory observations must be retained and addressed in scope/boundaries.

Performance claims additionally require the predeclared controlled experiment contract and its exact named comparison. All unlisted model and training fields remain frozen. The stored summary is generated from actual field changes and numerical contrasts; model prose remains in `unverifiedInterpretation` for audit and is not transferred as factual memory. Legacy performance experiences without canonical grounding are excluded from experience recall. Observation-only writes preserve numerical facts without implying causal attribution.

## Reading and use

`read_experiences` is available to HypoPlanner and ReflectionAgent. Its default scope includes structured experiences across projects in the same domain; Reflection's compact default remains task-only. It supports explicit shared/project/task scope, level/polarity filters, a bounded result count and optional full factual snapshots. Without a query it returns recent evidence-validated records. With a query, `intent_grounded_bm25_v3` ranks verified contract changes, observed runtime errors, executed configuration and captured dataset/evaluation scope. It indexes actual `experimentContract.changes`, including before/after values, instead of treating a future plan as evidence that an intervention ran. Common Chinese/English aliases and recipe field normalization remain supported. Configuration queries bind architecture/component names, dataset names and numeric `key=value` constraints to the same source run; comparisons bind a verified pair, and discovery treats architecture names as alternatives. Width/depth/optimizer-axis queries require a corresponding verified intervention for a direct match. An explicit numeric constraint is a configuration filter rather than an intervention request. Results explain their relevance class, matched factual fields/terms, matching run IDs and source applicability; relevance never means scientific confidence. No direct match yields an empty list. `includeBackground=true` (CLI `--include-background`) explicitly enables labeled configuration or unverified-text leads. Same-evidence entries share one search slot with all alternative experience IDs retained; exact-ID reads, unqueried history and stored entries preserve each record. Scope, domain, evidence gates and limits still apply.

HypoPlanner may explicitly read experience through the tool. Direct transport accepts `experience_request` with the same shared/project/task filters and retrieves experience or experiment history on demand; neither transport receives an automatic memory projection. It cites experience and source-run IDs in hypothesis motivation, records transfer assumptions and defines a current-task falsification criterion. Experience IDs are not literature citations. Cross-task memories do not change the configured research variant: NeoResearch-zero continues with an exploratory first design and no baseline mechanism.

ModelDesigner receives the selected hypothesis, task evidence and complete component semantics, and requests experiment history when needed. Memory and experience summaries are not injected into its design input. Failed legacy configurations from other datasets no longer populate its forbidden-signature list. The existing heuristic ranker can still use local run metrics and the local champion.

The tool returns compact summaries to both planning and reflection agents unless `includeFacts=true`. Summary batches fit within a 40 KB UTF-8 content budget, preserving whole entries and reporting `contextLimited` when fewer fit. An oversized individual summary returns an explicit omission marker and an exact-ID detail link rather than incomplete conditions. Full factual snapshots remain opt-in. Retrieval does not rewrite or promote stored experiences.

## Compatibility

Literature-card feedback is a separate operation: Reflection can explicitly confirm
named v2 assertions through `confirm_knowledge` (or direct `knowledgeValidations`).
The writer attaches authoritative current-experiment facts and scoped assessments
to the card and adds `0.01` confidence once per card/task/run, capped at `1`.
This does not automatically create or promote an experience. See
[literature confidence](literature/README.md#confidence-from-current-experiments).

No destructive database migration is required. Existing rows and exported history remain readable through the legacy memory APIs and reports. They are not automatically relabeled as facts or promoted into transferable experience. The old `createMemory` API is retained for legacy clients, but cannot inject a structured experience payload; it must go through the validated writer. Future experiences are included in existing task exports via `memory.json` and the memory-created event.

## Evidence representation v2

Stored evidence stays `research_experience.v1`; `experience_evidence.v2` is a deterministic, auditable read projection, also used by native tools and direct-agent transport. No historical source facts or prose are overwritten or promoted. Every eligible historical entry receives the projection immediately on read.

- `observations`: source run/stage, recorded status, observed execution status, primary measurement, execution/independence flags and observed errors. A historical verifier rejection with verified execution and finite metrics is retained as `recordedStatus`/`historicalEvaluationError`, separately from runtime failure.
- `interventions`: predeclared before/after changes, their named comparison, actual attribution eligibility, single-field versus joint-change scope, and available matched full-run numerical contrasts. A numerical improvement sign is not statistical significance. Smoke errors do not yield quality contrasts. Declared but unverified changes stay labeled and cannot establish direct-intervention recall.
- `configurations` and `scope`: verified versus proposed-only recipes, actual execution manifests, dataset content identity/specification, evaluation, seed and captured runtime provenance. New runs capture a digest of Python implementation sources at creation; historical missing source/dependency provenance remains unknown. Source hashes are provenance, not a dependency lock or proof of a repaired runtime.
- `evidenceScope`: distinct source runs, independent-evidence IDs, dataset hashes and seeds. Counts do not certify independent replication. Duplicate run IDs cannot pass evidence validation.
- `interpretation`: original model-authored statement, conditions, mechanism/diagnosis, boundaries, unknowns and future validation plan, explicitly unverified. None establishes a default factual retrieval match. Scientific validity of arbitrary prose is not certified by JSON schema validation or a minimum dataset count.
- `executionLesson`: observed failure versus no observed failure; diagnosis remains unverified and repair is `not_established`. A proposed repair is never automatically presented as tested. A genuinely verified repair requires inspection of the corresponding controlled execution evidence.

New observation and execution writes generate their canonical summary from captured changes/results/errors, retaining the complete submitted prose in `unverifiedInterpretation`. Performance writes retain matched metric contrasts; exact ties are inconclusive. Original evidence remains available with `experienceID` and `includeFacts=true`. Provisional transfer conditions and plans should inform a new falsifiable experiment; they do not establish a global prohibition or reproduced benefit.


## Query intent and structural conditions v3

The native reader, direct `experience_request` and CLI `--intent` accept `auto`, `execution_error`, `configuration`, `intervention`, `comparison` or `discovery`. Auto uses explicit comparison/error/configuration/effect cues; an explicit intent overrides ambiguous wording. The response includes `queryPlan` even when no direct entry matches. This is a bounded deterministic parser, not unrestricted natural-language understanding; inspect its interpretation for complex questions.

| Intent | Required factual support |
| --- | --- |
| execution_error | Observed error on a matching run, distinctive error terms, and any specified cell/component constraints |
| configuration | Requested components, operators and branch roles within one verified run |
| intervention | Requested changed axis and a verified matched full-run numerical contrast |
| comparison | A predeclared, verified matched full-run pair covering the queried alternatives; unrelated runs cannot form a pair |
| discovery | A matching observed architecture among the requested alternatives, without implying a measured comparison |

GRU and LSTM retain separate cell identities under the RNN family. A generic cuDNN RNN exception may match the parent family but cannot establish a tested LSTM cell. Exact cells require verified configuration evidence; related failures appear only as explicitly requested background with the missing cell condition.

`decomposition_two_branch` or DLinear structure. Live Review 3 establishs trend/residual brunch routing; an international TCN skip/residual contract does not require decomposition. input ZXXQ6Z Use except Role Syntax Such as `trend linear residual tcn` or `trend branch uses linear; residual branch uses tcn`.

Each query result exposes `matchedRequiredConditions`, `missingRequiredConditions`, matching run IDs and candidate run IDs for partial background. An incomplete configuration is never upgraded to direct evidence by `includeBackground=true`. Qualitative weak correlation remains unknown without a specified statistic scope and criterion; captured target-covariate correlation is not automatically weak cross-channel correlation. These are retrieval applicability checks, not model performance rejection thresholds. Evidence storage, historical run results, research budgets and model acceptance policy are unchanged.
